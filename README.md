# ТУРБОНАЙЗЕР

Telegram-бот ищет артикулы по Turbo P/N, OEM, JRONE, FLP и другим
номерам из компактной поисковой базы `turbo_search.sqlite`. Запрос можно отправить текстом или
фотографией шильдика.

## Установка

```powershell
py -m pip install -r requirements.txt
```

RapidOCR работает локально через ONNX. Для сервера без доступа к интернету
модели нужно скачать во время сборки:

```powershell
rapidocr download_models
```

Для серверного развёртывания рекомендуется использовать `Dockerfile`: он
устанавливает системные библиотеки OpenCV и проверяет инициализацию RapidOCR
ещё во время сборки контейнера.

```powershell
docker build -t database-bot .
docker run --rm -e API_TOKEN="токен Telegram-бота" database-bot
```

Для постоянного запуска используйте `compose.yaml` и файл `.env`:

```env
API_TOKEN=токен Telegram-бота
```

```powershell
docker compose up -d --build
```

Контейнер ограничен по CPU, памяти, количеству процессов и размеру временного
каталога. В самом боте одновременно обрабатывается только одна фотография:
не более трёх фото в минуту от пользователя и не более двенадцати фото в минуту
суммарно. Принимаются изображения до 8 МБ и 16 мегапикселей. Текстовый поиск
также защищён отдельными пользовательским и общим лимитами.

## Поиск по VIN

Бот распознаёт 17-значный VIN как отдельный тип запроса. Проверенные результаты
хранятся в `vin_verified.json` и при запуске импортируются в постоянный
SQLite-кэш `/data/vin_cache.sqlite`.

VIN-поиск доступен только Telegram-пользователям из белого списка. Укажите их
числовые ID через запятую в `.env`:

```dotenv
VIN_ALLOWED_USER_IDS=123456789,987654321
VIN_ADMIN_USER_IDS=123456789
```

Для допущенных пользователей нет пользовательской, общей или суточной квоты
VIN-запросов. Интернет-поиски выполняются последовательно по одному: если уже
идёт другой VIN-запрос, следующий ожидает освобождения очереди. Ограничения
обычного текстового поиска и поиска по фотографиям при этом сохраняются.

Для одного пользователя можно настроить сообщение после его первого поискового
запроса за календарный день по московскому времени. Это работает для поиска по
текстовому номеру, VIN и фотографии:

```dotenv
DAILY_GREETING_USER_ID=123456789
DAILY_GREETING_TEXT=Персональное сообщение
```

Отметка дня хранится в SQLite и сохраняется после перезапуска контейнера.
Сообщение отправляется отдельным последним сообщением после результатов поиска.

Если VIN уже проверен, бот показывает автомобиль, позиции турбокомпрессоров,
OEM-номера, Turbo P/N, артикулы картриджей из основной базы и ссылки на
источники.

Неизвестный VIN сначала бесплатно декодируется через NHTSA vPIC. Затем бот
делает в Yandex Search несколько коротких точных запросов по полному VIN и его
модельному префиксу с обязательным фильтром `site:emex.ru`, после чего
YandexGPT структурирует найденные сниппеты. Результаты с любых других доменов
отбрасываются. Каждый возвращённый OEM/Turbo P/N дополнительно отбрасывается,
если его нет дословно ни в одном поисковом источнике. Возможные номера
сопоставляются точным поиском с основной SQLite-базой, а ответ сохраняется в
кэш и очередь ручной проверки. Такой
результат всегда помечается как предварительный: перед заказом номер нужно
сверить с шильдиком турбины или официальным каталогом. При таком запросе VIN
передаётся NHTSA и настроенному поисковому провайдеру.

Для основного онлайн-поиска создайте API-ключ в
[Yandex AI Studio](https://aistudio.yandex.ru/) и добавьте в `.env`:

```dotenv
YANDEX_API_KEY=replace-with-your-key
YANDEX_FOLDER_ID=replace-with-your-folder-id
YANDEX_SEARCH_TYPE=SEARCH_TYPE_RU
YANDEX_MODEL=yandexgpt/rc
```

Сервисному аккаунту нужны роли `search-api.webSearch.user` и
`ai.languageModels.user`, а ключу — области действия `yc.search-api.execute` и
`yc.ai.foundationModels.execute`. Ключ, созданный непосредственно в AI Studio,
получает необходимые разрешения автоматически. `YANDEX_FOLDER_ID` должен быть
идентификатором каталога именно этого сервисного аккаунта. Допустимые типы
поиска: `SEARCH_TYPE_RU`, `SEARCH_TYPE_COM`, `SEARCH_TYPE_KK`,
`SEARCH_TYPE_BE` и `SEARCH_TYPE_UZ`.

В production используется только Yandex Search по Emex. Gemini и другие
источники в рабочий маршрут не входят. Без полностью настроенного Yandex
проверенные VIN и очередь продолжают работать, но интернет-поиск отключён.
Одновременно выполняется не более одного онлайн-поиска. Повторный VIN берётся
из SQLite-кэша без нового платного обращения.

Результаты и очередь ручной проверки хранятся в `/data/vin_cache.sqlite`.
Запросы, для которых не удалось получить ни одного обоснованного номера
турбины, дополнительно записываются в отдельную базу
`/data/vin_unresolved.sqlite`. Она не содержит Telegram ID, chat ID и другие
данные пользователя, сделавшего запрос. Повторные запросы одного VIN
увеличивают его счётчик. Если позднее VIN успешно обрабатывается, он удаляется
из этой базы.

Для новых неразобранных VIN бот один раз отправляет уведомление каждому
администратору из `VIN_ADMIN_USER_IDS`. В служебной базе сохраняются только ID
чата администратора и ID этого уведомления, чтобы связать ответ с VIN. Ответьте
на уведомление прямо в Telegram:

```text
Левая: KP39-015
Правая: KP39-020
OEM левая: A6560900380
Источник: https://emex.ru/...
Комментарий: проверено вручную
```

Достаточно одной строки с турбиной или OEM. Поля `Источник` и `Комментарий`
необязательны. Администратор также может отправить отдельное сообщение с VIN и
теми же строками. Бот сохранит результат как проверенный в
`/data/vin_cache.sqlite`, удалит VIN из очереди и сразу покажет сохранённый
ответ. Следующие запросы этого VIN обслуживаются из SQLite без интернет-поиска.

### Фоновый VIN-наблюдатель

Наблюдатель периодически повторно проверяет неразобранные VIN только через
Yandex Search по Emex. Он выполняет строго один поиск за раз, не чаще одного
VIN за заданный интервал и соблюдает постоянный суточный лимит:

```dotenv
VIN_OBSERVER_ENABLED=false
VIN_OBSERVER_INTERVAL_SECONDS=900
VIN_OBSERVER_DAILY_LIMIT=5
VIN_OBSERVER_RETRY_SECONDS=86400
```

После неудачного пользовательского поиска первая повторная проверка назначается
через `VIN_OBSERVER_RETRY_SECONDS`. Старые записи очереди проверяются после
включения наблюдателя. При повторных неудачах интервал увеличивается до семи
дней. Суточный счётчик и расписание хранятся в
`/data/vin_unresolved.sqlite`, поэтому перезапуск контейнера не сбрасывает
ограничения.

Если наблюдатель находит возможные номера, он сохраняет предварительный
результат в SQLite и присылает администратору отдельное сообщение. Ответ
`Подтверждаю` переводит найденный результат в проверенный. Также можно ответить
строками с исправленными номерами. Автоматически найденные сведения не получают
статус проверенных без подтверждения администратора.

На production этот серверный режим выключен: повторную проверку очереди
выполняет запланированная задача текущего Codex-чата без обращения к API из
бота. Переменную `VIN_OBSERVER_ENABLED` не следует включать одновременно с
Codex-наблюдателем.

Очереди и статистику можно посмотреть внутри контейнера:

```powershell
docker exec database-bot python vin_admin.py stats
docker exec database-bot python vin_admin.py pending
docker exec database-bot python vin_admin.py unresolved-stats
docker exec database-bot python vin_admin.py unresolved --limit 100
docker exec database-bot python vin_admin.py export-unresolved --limit 1000
docker cp database-bot:/data/vin_unresolved_export.csv .
```

Новые подтверждённые соответствия добавляются в `vin_verified.json`, проходят
проверку и доставляются обычным обновлением контейнера. Docker volume `vin-data`
сохраняет обе VIN-базы при пересборке и замене контейнера.

## Запуск

```powershell
$env:API_TOKEN="токен Telegram-бота"
py script.py
```

По умолчанию используется `turbo_search.sqlite` рядом со скриптом. Другой
путь можно передать через `DATABASE_PATH`:

```powershell
$env:DATABASE_PATH="D:\path\to\turbo_parts.sqlite"
py script.py
```

Если хостинг клонирует репозиторий без Git LFS, бот автоматически распознает
LFS-указатель и загрузит настоящую SQLite-базу из GitHub в системный временный
каталог. Адрес и каталог кеша можно переопределить переменными
`DATABASE_DOWNLOAD_URL` и `DATABASE_CACHE_DIR`.

`turbo_search.sqlite` содержит все данные, используемые поиском, и хранится в
обычном Git. Полная `turbo_parts.sqlite` остаётся исходной базой в Git LFS.
Пересобрать компактную базу можно командой:

```powershell
py build_search_database.py
```

Для поиска по изображению отправьте фото или файл изображения. Лучше всего
работают крупные резкие снимки без бликов, где номер расположен горизонтально.
